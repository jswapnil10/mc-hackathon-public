LIVE ARENA EXPLAINER

What happens after you click
Start battle?

Every label in the progress panel represents a real backend milestone. This guide explains what is executing, what information it receives, and what kind of output it produces.

Important boundary

The UI shows structured decisions and audit summaries—not private chain-of-thought. Fraud labels remain sealed from Blue until the Referee scores the completed case.

00Preparing → 01Red plans → 02Arena builds → 03Blue decides → 04Referee scores → 05Adaptation* → 06Report ready

*Adaptation exists only when two or three feedback rounds are selected.

00
REQUEST SETUP

Preparing the synthetic arena

NO MODEL OUTPUT YET

What happens

The server validates the selected attack family, difficulty, number of rounds, and seed. It confirms that no other battle is already running, loads the model configuration, and creates a private progress record for this browser run.

What it receives

  • Attack family
  • Difficulty
  • One to three rounds
  • Random seed and progress ID

Output represented

A temporary run-status message:

status · stage · round_number · total_rounds

It means “the request is valid and accepted.” No attack plan or payment event exists yet.

01
GENAI RED AGENT

Red designs a bounded attack plan

ONE PLAN PER ROUND

What happens

Red receives a safe attack-family card and asks the open model for a structured plan. A deterministic compiler converts that plan into a scenario, and a safety gate rejects parameters, identifiers, or behaviors outside the simulator’s approved bounds.

What it receives

  • Selected family and difficulty
  • Allowed stages and parameter bounds
  • Source-backed attack context
  • Coarse prior-round feedback, only from round two onward

Output represented

red.plan

Objective, target payment phase, focus stages, bounded parameter changes, adaptation goal and hypothesis.

red.scenario

Scenario ID, ordered stage templates, safe parameters, controls and safety constraints.

02
DETERMINISTIC SYNTHETIC ARENA

The arena materializes payment events

NO NEW MODEL CALL

What happens

The simulator turns Red’s scenario into an ordered customer journey. It also creates legitimate look-alike cases to test whether Blue causes unnecessary customer friction. Observable behavior and the answer key are created as separate objects.

What Blue can see

  • Event type and simulated time
  • Payment lifecycle phase
  • Observable signals and attributes
  • Prior events inside the same isolated case

Blue cannot see attack labels, scenario truth, value at risk, or intervention answers.

Output represented

simulation.attack_case.events

Ordered observable events for the attack case.

legitimate_control_count

The number of hard legitimate look-alikes.

sealed truth

Attack labels and value consequences reserved for the Referee.

03
TWO-SPEED BLUE DEFENSE

Blue investigates and acts on each event

ONE TURN PER REACHED EVENT

What happens

The fast detector and sequence guard produce immediate risk signals. The Blue open-model investigator reviews the observable event and evidence packets, then proposes an action. A policy gate checks that action before it is accepted.

A block ends that isolated case. A hold is temporary, so later events may still be evaluated.

Possible decisions

  • Allow: continue normally
  • Monitor: watch for a pattern
  • Step up: request stronger verification
  • Hold: pause value movement temporarily
  • Block: stop the case

Output represented

blue.attack_turns[]

For each reached event: investigation focus, requested evidence tools, evidence packets, action, risk level, confidence, reason codes, mitigation, detector signals and policy adjustments.

The live counter means completed Blue decisions—not model tokens or rotating status text.

04
DETERMINISTIC REFEREE

The Referee opens sealed truth and scores the run

NO MODEL JUDGMENT

What happens

Only after Blue finishes, the Referee compares Blue’s decisions with the sealed attack and legitimate-case truth. It calculates whether the attack was stopped, when the first useful response happened, how much value was protected, and whether legitimate users were harmed.

Outcome meanings

  • Prevented: no synthetic value was lost
  • Contained: some loss occurred but was limited
  • Detected: Blue warned, without proven value protection
  • Missed: no actionable warning

Output represented

referee

Outcome, overall defense score, attack strength, simulated detection time, value at risk, value protected, money lost, customer-friction rates and per-stage lifecycle scores.

feedback_released_to_red

Only outcome, detected stage, timing, protected ratio, false-positive rate and coarse reason categories.

05
OPTIONAL FEEDBACK LOOP

Blue tests an update; Red evolves next round

ONLY FOR 2–3 ROUNDS

What happens

Blue’s strategist proposes a new defense playbook from post-outcome evidence. The candidate is replayed against the same attack and legitimate controls. A deterministic promotion gate accepts it only if it improves measurable defense without increasing customer harm.

Separately, Red receives its smaller coarse feedback packet and creates a child scenario in the next round.

Promotion checks

  • Defense score does not fall
  • Protected value does not fall
  • Lifecycle weakness does not worsen
  • Legitimate friction does not rise
  • At least one measurable gain exists

Output represented

blue_adaptation

Proposed playbook, replay decisions, replay score, promoted true/false, and the promotion reason.

next round red.scenario

Parent scenario ID, mutation number, adaptation hypothesis and new bounded parameter choices.

06
AUDIT RECORD

The report is assembled and saved

RUN COMPLETE

What happens

The orchestrator assembles every completed round into one auditable run record, saves the latest result, and returns it to the browser. The UI then opens the Battle Report, Payment Journey Scorecard, impact view, and event-by-event replay.

What the viewer receives

  • Run ID and duration
  • Model configuration
  • Red plan and synthetic scenario
  • Blue event decisions
  • Referee metrics
  • Final promoted defense playbook

Output represented

LabRun

run_id, architecture, model configuration, all round results, final defense playbook, submission profile and wall-clock duration.

This is the complete JSON object behind the visual Battle Report.

WALL-CLOCK ELAPSEDHow long your browser has waited

This includes local-model generation and server processing.

SIMULATED DETECTION TIMEWhere Blue reacted in the synthetic story

“Detected at 20s” refers to event offsets inside the scenario—not 20 seconds of real waiting.

UP TO N EVENTSThe maximum events available for review

The final count can be lower because a decisive block ends an isolated case early.
